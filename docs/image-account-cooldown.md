# 生图账号冷却

后台「生图账号冷却时间」默认 30 分钟，配置键为 `image_account_cooldown_minutes`。接受非负整数，0 关闭。启用时单账号有效生图并发为 1，原并发配置保留，关闭后恢复。

每次确认生图成功，沿用原有额度扣减，并在同一次保存中写入 UTC 冷却截止时间，然后释放账号占用。例如 25 → 24 后立即冷却。冷却结束后仍需满足原有账号资格条件。

开启冷却时，上游消息去除首尾空白后完全等于 `I wasn't able to generate the image due to an error on my side.`，也会让所用账号从收到错误时开始冷却 N 分钟。此操作只更新冷却字段，不修改额度、账号状态、成功数、失败数或 429 记录。其他大小写、标点或附加说明不匹配。

该指定错误允许每张图片最多追加一次其他账号的生图尝试：A 冷却后排除 A，若从本张图片首次选号起尚未满 20 秒，则尝试 B。选号和提交前均检查窗口；无其他账号或窗口结束时返回 A 的原始错误和邮箱。B 已在窗口内开始生成后，仍使用原请求总超时，可以超过 20 秒完成。B 成功则正常扣额度并冷却；B 再次命中同一错误则也冷却，返回 B 的错误；B 返回其他错误也直接结束，不再换 C。文本回复模式保留原消息返回形式。

冷却设置为 0 时不启用此特殊错误冷却和换号。未进入特殊换号分支的非 400 错误保留原有 20 秒重试规则，其他 400 直接返回。已经收到图片结果后不重复提交生成，避免产生重复图片。

## 最终无图回复的限流归零规则

以下规则属于账号限流，独立于冷却配置，即使 `image_account_cooldown_minutes=0` 也生效。仅在本张图片最终没有结果时检查上游回复，不检查用户输入或中间工具参数；已有图片优先，现有图片轮询和恢复流程继续保留。

- 工具参数文本：去除首尾空白和完整 Markdown 代码块/加粗包裹后，以 `{` 开头、以 `}` 结尾，同时包含 `"size":`、`"n":`、`"prompt":` 三个字段标记。字段顺序、冒号周围空白、字段值和其他字段不限，不要求完整 JSON 解析成功；缺少闭合 `}` 不匹配。参数里的 `referenced_image_ids` 是输入参考图，不作为生成结果。
- 英文提示：合并空白后，精确等于 `It looks like image creation is temporarily unavailable. Do you want to try something else?`、`Generate this image later`、`Schedule this image for free, or upgrade to create it now.`，或后两句按标题、说明顺序合并的内容。

命中后复用额度耗尽记账：`status=限流`、`quota=0`、`image_quota_unknown=false`、`fail` 增加一次，`success` 和 `rate_limit_429` 不变；不新增、延长或清除冷却时间。账号退出调度和可用额度统计。“全部解冻”只清理冷却记录，不能恢复此限流状态或零额度。开启“自动移除限流账号”时沿用现有移除流程，否则保留账号，使用现有恢复检查及上游资料刷新，不按冷却分钟数自动恢复。

换号沿用每张图片从首次选号起的 20 秒窗口，等待、选号和提交前复核时间，已启动的替代请求可在原请求总超时内完成。若已经处于指定错误冷却后的第二次尝试，命中限流后结束，不再额外换号。没有替代账号或窗口结束时保留最后一次限流错误及其邮箱、会话信息。

对外返回 `429`、`code=image_quota_exhausted`、`type=insufficient_quota`。英文提示保留原文；参数 JSON 返回“临时生成错误，请重试”。调用日志的 `error` 使用可读说明，原始参数放在同一条日志的 `raw_upstream_message` 中，不重复写入长文本，也不记录全量 SSE。原来显示 `upstream_text_reply / 400` 的匹配回复会改为该限流分类。

不新增数据库字段、管理接口、定时器、全量账号扫描或上游探测。数据库复用单账号事务，JSON 沿用一次完整文件保存成本；普通、流式、后台任务及多图请求共用同一记账入口。

## 冷却配置调整

修改正数会按账号原触发时间（生图成功或指定错误）重算仍在冷却的截止时间；没有开始时间的旧记录按旧配置推算，无法推算时以修改时刻为起点。关闭时忽略冷却限制但保留记录，重新启用后仍未到期的记录继续生效。管理员可使用“解冻全部冷却账号”清除历史记录；应用重启不会清空冷却。

不统一隔离或探测老账号；上线后自然请求，成功后开始冷却。外部系统直接拿账号调用上游不受本项目内部调度约束。

## 仪表盘和接口

`/health` HTML 页面新增「冷却中账号」和按后台配置显示的「N分钟内解冻」（配置为 0 时显示「冷却已关闭」）。后一项仅统计当前符合生图资格且 `现在 < 截止时间 ≤ 现在 + 配置分钟数` 的账号；包含沿用原规则可用的未知额度账号，不包含已禁用或已耗尽额度的账号。

管理员鉴权接口 `GET /api/accounts/image-cooldown-metrics` 返回：

```json
{
  "cooling_accounts": 100,
  "thawing_within_hour": 80,
  "cooldown_minutes": 30,
  "next_thaw_at": 1791100800.0,
  "as_of": 1791099000.0
}
```

时间为 UTC Unix 秒；无冷却账号时 `next_thaw_at` 为 `null`。统计缓存 15 秒，共享缓存刷新竞争时可以返回最多 30 秒的已有快照，`as_of` 标识统计时刻。页面 30 秒刷新，隐藏页面暂停刷新。

管理员 `POST /api/accounts/image-cooldown/clear` 一次清除全部冷却记录并返回清除数量及最新统计。正常账号列表、原额度统计、`/api/accounts/image-pool-metrics`、`/health?format=json` 保留原有口径；内部冷却字段不会出现在原账号接口中。冷却账号仍为正常账号，剩余额度不受冷却影响。

没有可调度账号时，生图请求返回 `503`、错误码 `image_pool_unavailable` 和 `Retry-After`，错误消息包含可获得的号池最早解冻时间。时间基于当前号池快照，不保证指定套餐/来源在该时刻一定空闲；忙碌或依赖故障且无解冻时间时，重试间隔为 1 秒。单张和多张请求全部遇到该错误时均保留此分类。

## 资源和部署

- 数据库候选查询使用 `(image_cooldown_until, access_token_hash)` 索引和游标分页，每批最多 128 条，各请求消费候选批次；128 不是并发上限。
- 领取后重新读取单个账号，避免另一个进程的成功结果被旧候选缓存绕过。不会为冷却新增上游预检。
- 不为账号创建等待任务、定时器或周期扫描，不在上游生图期间持有数据库事务。成功写入合并到原有结果保存。
- 所有账号冷却时，短暂合并空结果查询并及时返回，不反复轮询。数据库统计直接聚合，不加载完整账号资料。
- JSON/Git 仅支持单进程冷却调度，维护轻量排序索引。原有全文件保存成本仍然存在；2 万账号、100–400 并发优先使用数据库和 Redis。
- 多进程必须使用数据库和共享 Redis。Redis 不可用时停止新领取，避免回退到各进程独立状态。任务异常退出时，占用期限包含任务时间和一段冷却时间，防止立即复用。
- 已成功但保存失败时记录 `image_success_bookkeeping_failed` 并保留占用直到其保守期限，返回已生成图片，不重复提交。若 Redis 数据也丢失，未成功持久化的这部分信息无法恢复。
- 指定错误命中时增加一次单账号数据库事务；JSON/Git 增加一次完整账号文件保存。不清空候选游标或逐账号新增审计日志，统计沿用缓存刷新周期。冷却保存失败时记录 `image_error_cooldown_bookkeeping_failed` 并保留保守占用期限，避免马上重复领取。
- 冷却开启期间建议所有生图调用通过同一号池调度；配置的 `UVICORN_WORKERS` 应与实际工作进程数一致。

升级前备份账号数据库和配置。停止旧工作进程后更新并统一启动，启动时自动新增默认值为 0 的冷却列及索引；不要让新旧调度进程同时服务。无需给老账号补历史冷却。需要停用时将冷却分钟数设为 0。

## 离线验证

功能测试不调用真实上游：

```powershell
uv run --with 'fakeredis[lua]' python -m unittest test.test_image_cooldown
uv run --no-sync python -m unittest test.test_final_image_reply_limit
uv run --with psutil python -m scripts.benchmark_image_cooldown
```

Redis 测试运行真实 Lua 脚本并覆盖两个独立进程通过模拟 Redis 协议服务共享占用。未安装 fakeredis 时，这两项测试会显式跳过。

压测使用临时 SQLite 和内存占用状态，2 万模拟账号，100/200/400 同时领取；比较关闭与开启冷却，并覆盖 90% 和全部账号冷却。报告写入 `build/image-cooldown-benchmark.json`，包含 CPU 时间、RSS 变化、选号 P50/P95、SQL 次数、重复领取及实际查询计划。RSS 变化是批次前后快照，不代表峰值内存。

这衡量的是本机调度成本，不包含上游生成时间，也不能替代生产 PostgreSQL/Redis、网络和完整请求链路的容量测试。持续 400 并发还要求足够账号周转；平均生图 2 分钟、冷却 30 分钟时，理论上约需 6,200 个有额度的账号，另需预留失败重试余量。
