# 生图成功后冷却

后台「生图成功后冷却时间」默认 60 分钟，配置键为 `image_account_cooldown_minutes`。接受非负整数，0 关闭。启用时单账号有效生图并发为 1，原并发配置保留，关闭后恢复。

每次确认生图成功，沿用原有额度扣减，并在同一次保存中写入 UTC 冷却截止时间，然后释放账号占用。例如 25 → 24 后立即冷却。普通失败、通用 400 文案不会触发成功冷却，也不会因此新增清零额度操作。冷却结束后仍需满足原有账号资格条件。

修改正数仅影响后续成功的任务，既有截止时间不重算。关闭时忽略冷却限制但保留记录，重新启用后仍未到期的记录继续生效。应用重启不会清空成功后的冷却。

不统一隔离或探测老账号；上线后自然请求，成功后开始冷却。外部系统直接拿账号调用上游不受本项目内部调度约束。

## 仪表盘和接口

`/health` HTML 页面新增「冷却中账号」和「未来 1 小时内冷却结束」。后一项仅统计当前符合生图资格且 `现在 < 截止时间 ≤ 现在 + 3600 秒` 的账号；包含沿用原规则可用的未知额度账号，不包含已禁用或已耗尽额度的账号。

管理员鉴权接口 `GET /api/accounts/image-cooldown-metrics` 返回：

```json
{
  "cooling_accounts": 100,
  "thawing_within_hour": 80,
  "next_thaw_at": 1791100800.0,
  "as_of": 1791099000.0
}
```

时间为 UTC Unix 秒；无冷却账号时 `next_thaw_at` 为 `null`。统计缓存 15 秒，共享缓存刷新竞争时可以返回最多 30 秒的已有快照，`as_of` 标识统计时刻。页面 30 秒刷新，隐藏页面暂停刷新。

正常账号列表、原额度统计、`/api/accounts/image-pool-metrics`、`/health?format=json` 保留原有口径；内部冷却字段不会出现在原账号接口中。冷却账号仍为正常账号，剩余额度不受冷却影响。

没有可调度账号时，生图请求返回 `503`、错误码 `image_pool_unavailable` 和 `Retry-After`，错误消息包含可获得的号池最早解冻时间。时间基于当前号池快照，不保证指定套餐/来源在该时刻一定空闲；忙碌或依赖故障且无解冻时间时，重试间隔为 1 秒。单张和多张请求全部遇到该错误时均保留此分类。

## 资源和部署

- 数据库候选查询使用 `(image_cooldown_until, access_token_hash)` 索引和游标分页，每批最多 128 条，各请求消费候选批次；128 不是并发上限。
- 领取后重新读取单个账号，避免另一个进程的成功结果被旧候选缓存绕过。不会为冷却新增上游预检。
- 不为账号创建等待任务、定时器或周期扫描，不在上游生图期间持有数据库事务。成功写入合并到原有结果保存。
- 所有账号冷却时，短暂合并空结果查询并及时返回，不反复轮询。数据库统计直接聚合，不加载完整账号资料。
- JSON/Git 仅支持单进程冷却调度，维护轻量排序索引。原有全文件保存成本仍然存在；2 万账号、100–400 并发优先使用数据库和 Redis。
- 多进程必须使用数据库和共享 Redis。Redis 不可用时停止新领取，避免回退到各进程独立状态。任务异常退出时，占用期限包含任务时间和一段冷却时间，防止立即复用。
- 已成功但保存失败时记录 `image_success_bookkeeping_failed` 并保留占用直到其保守期限，返回已生成图片，不重复提交。若 Redis 数据也丢失，未成功持久化的这部分信息无法恢复。
- 冷却开启期间建议所有生图调用通过同一号池调度；配置的 `UVICORN_WORKERS` 应与实际工作进程数一致。

升级前备份账号数据库和配置。停止旧工作进程后更新并统一启动，启动时自动新增默认值为 0 的冷却列及索引；不要让新旧调度进程同时服务。无需给老账号补历史冷却。需要停用时将冷却分钟数设为 0。

## 离线验证

功能测试不调用真实上游：

```powershell
uv run --with 'fakeredis[lua]' python -m unittest test.test_image_cooldown
uv run --with psutil python -m scripts.benchmark_image_cooldown
```

Redis 测试运行真实 Lua 脚本并覆盖两个独立进程通过模拟 Redis 协议服务共享占用。未安装 fakeredis 时，这两项测试会显式跳过。

压测使用临时 SQLite 和内存占用状态，2 万模拟账号，100/200/400 同时领取；比较关闭与开启冷却，并覆盖 90% 和全部账号冷却。报告写入 `build/image-cooldown-benchmark.json`，包含 CPU 时间、RSS 变化、选号 P50/P95、SQL 次数、重复领取及实际查询计划。RSS 变化是批次前后快照，不代表峰值内存。

这衡量的是本机调度成本，不包含上游生成时间，也不能替代生产 PostgreSQL/Redis、网络和完整请求链路的容量测试。持续 400 并发还要求足够账号周转；平均生图 2 分钟、冷却 60 分钟时，理论上约需 12,400 个有额度的账号，另需预留失败重试余量。
